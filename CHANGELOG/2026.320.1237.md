# 2026.320.1237 — fix(pins): advance pod-ollama to v2026.320.1029 in the ollama-rocm backend

## Summary

One line: this candy's `require:` moves `pod-ollama:v2026.274.0620 → v2026.320.1029`, the
tag pod-ollama published when `OLLAMA_VERSION` reached v0.40.16 (opencharly/pod-ollama#8).

The AMD sibling of opencharly/layer-ollama-cuda#7, same reason and same order: this candy
is the ROCm backend ADD-ON to the ollama candy, so its `require:` decides which ollama the
HIP runner attaches to, and it still named the pre-bump candy.

Like the CUDA leg, it cannot move after the box: with this `require:` at the new tag and a
composing box still pinning the old one, the loader refuses the project (`resolved to
multiple git tags with differing content within one scope`). Producer-first order: this
pin → this repo's tag → `distro-cachyos`'s `box/ollama-rocm` moves BOTH of its refs in one
change.

`exclude_distro` was argued for.** That PR added `ollama-version-pinned` with
`exclude_distro: [arch, cachyos]`, defended in its body from the schema and the image's
distro tags. This bed is the CachyOS side of that claim, and the runner reports exactly

```

```

A SKIP here is the design, not a hole: on CachyOS the `ollama` package supplies the
server and `pacman` owns the version, so the pin does not bind — and the tarball path,
where it does bind, runs the step (that is the Fedora evidence on pod-ollama#8 and
distro-fedora#121). The skip is also enumerated by the runner, so it cannot hide a
changed-path assertion.

**4. Scope boundary, stated so a green run is not over-read.** This is the bed that proves
`ollama-rocm` COMPOSITION, the backend library shipping, and the server reaching steady
state. On a host with no AMD card it does not prove AMD inference — the bed's own comment
says the same, and `ollama` falls back to CPU there, which is why the inherited runtime
checks still pass.
